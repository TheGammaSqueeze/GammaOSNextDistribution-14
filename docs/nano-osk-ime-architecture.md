# GammaOS Nano OSK: Multi-Script IME Architecture and Phase Plan

Status: active build blueprint. Companion to `nano-leanback-osk-spec.md` (the
Latin-core spec). This document covers the EXPANDED scope agreed with the
product owner: a full multi-script input method, not just a 1:1 Leanback port.
No em-dashes or en-dashes; ASCII hyphen only.

## Scope decisions (locked)

1. Language scope: FULL. Latin (16 Leanback layouts + accents) PLUS real CJK
   input (Chinese Pinyin to Hanzi, Japanese romaji/kana to Kanji, Korean Hangul)
   PLUS Arabic (contextual shaping + RTL/BiDi) and the other RTL/complex scripts
   (Hebrew, plus Cyrillic/Greek/Thai grids).
2. Accent long-press popups: INCLUDED (Leanback diacritic popups, native).
3. Layout selection: BOTH. Default to the Nano UI language at open AND provide an
   in-keyboard language switch key to change script on the fly.
4. Text editing: REAL CARET (mid-string insert/delete; Left/Right + L1/R1 move
   the caret).

## Why this is more than a Leanback port

Leanback is Latin-only with no predictive engine. Real CJK/Arabic input forces
three things the Latin spec deliberately omitted:

- A COMPOSING (pre-edit) buffer distinct from the committed text. Pinyin letters,
  romaji, and Hangul jamo accumulate in a composing region before they resolve
  to Hanzi/Kanji/syllables.
- A navigable CANDIDATE BAR (Pinyin -> Hanzi list, Kana -> Kanji list).
- Per-script text rendering: Arabic/Hebrew need RTL ordering (ICU ubidi) and
  Arabic needs contextual shaping (ICU u_shapeArabic to presentation forms),
  because the existing `drawText` lays codepoints left-to-right with no shaping.

So the architecture is: a Leanback-style keyboard (physical keys + navigation)
plus a pluggable per-script INPUT METHOD layer (composition + candidates) plus a
script-aware TEXT FIELD renderer (LTR direct, or RTL+shaped).

## Engine inventory (verified in tree)

- ICU present at `external/icu` (`libandroidicu`). Provides `ubidi_*` (BiDi
  reordering) and `u_shapeArabic` (Arabic Presentation Forms). This is the
  Arabic/Hebrew path. No HarfBuzz glyph-index plumbing needed: shape to
  presentation-form codepoints, reorder to visual order, feed the existing
  codepoint-based `drawText` (Noto Naskh Arabic has the PF glyphs).
- HarfBuzz present at `external/harfbuzz_ng` (fallback if PF shaping proves
  insufficient for ligatures beyond lam-alef).
- NO AOSP PinyinIME and NO mozc in tree. Chinese needs a vendored engine +
  dictionary (libgooglepinyin: compact C++ engine + `dict_pinyin.dat` ~1.3MB).
  Japanese Kanji conversion needs a vendored dictionary engine (hardest piece).
- FreeType atlas already loads Noto CJK, Noto Naskh Arabic, color emoji, so all
  glyphs render once we feed the right codepoints.

## Runtime architecture

### Components

- `NanoOskTypes.h` (hand-written): Key/Row/Keyboard/Popup structs, code/glyph
  enums. STABLE.
- `NanoOskLayouts.h` (GENERATED by `tools/osk/gen_osk_layouts.py`): the 16 ABC +
  5 SYM Leanback keyboards + 49 popups as fraction-geometry tables. DONE.
- `NanoOsk.h` / `NanoOsk.cpp`: the keyboard runtime. Owns the aspect-aware box,
  rendering, geometric D-pad navigation, shift/sym/caps state, accent popups,
  the committed buffer + caret, the composing buffer, the candidate bar, and the
  active `InputMethod`. Exposes the keep-stable public API
  (`openOsk`/`closeOsk`/`oskType`/`oskBackspace`/`oskConfirm`/`renderOsk`/
  `openOskForPassword`/`updateSearchResults`) so existing callers are untouched.
- `InputMethod` interface (per-script plugin):
  ```
  struct InputMethod {
    virtual ScriptDir direction() const;          // LTR or RTL
    virtual bool wantsCandidates() const;          // shows candidate bar
    // returns true if the engine consumed the key (composing); false to let
    // the keyboard commit the codepoint directly.
    virtual bool onCodepoint(uint32_t cp, OskBuffer& buf);
    virtual bool onBackspace(OskBuffer& buf);      // edit the composing region
    virtual const std::vector<std::string>& candidates() const;
    virtual void chooseCandidate(int index, OskBuffer& buf);
    virtual std::string composingText() const;     // pre-edit display
    virtual void reset();
  };
  ```
  Implementations: `LatinInput` (direct, accents), `HangulInput` (jamo
  automaton), `CyrillicInput`/`GreekInput`/`ThaiInput`/`HebrewInput` (direct +
  script dir), `ArabicInput` (direct, RTL, shaping applied at render),
  `PinyinInput` (libgooglepinyin), `JapaneseInput` (romaji->kana + kanji dict).
- Text-field renderer: `renderField(text, caret, dir)` - LTR draws as today;
  RTL runs `ubidi` reordering and, for Arabic, `u_shapeArabic` first.

### Language to (layout + input method) map

`pickInput(localeCode, region)` returns `{ LayoutChoice, InputMethod* }`:
- Latin locales -> Leanback `LayoutChoice` (qwerty_*/qwertz*/azerty) + `LatinInput`.
- ru -> Cyrillic grid + `CyrillicInput`; el -> Greek grid + `GreekInput`;
  th -> Thai grid + `ThaiInput`; he -> Hebrew grid + `HebrewInput` (RTL);
  ar -> Arabic grid + `ArabicInput` (RTL + shaping).
- ko -> a Latin-position Hangul grid + `HangulInput`.
- zh -> qwerty_us + `PinyinInput` (Latin keys, Hanzi candidates).
- ja -> qwerty_us + `JapaneseInput` (romaji, kana/kanji candidates).
The in-keyboard language switch cycles a curated set (UI language + the common
ones) without changing the system locale.

## Phase plan (tractability-ordered; each phase is shippable)

Phase A - Foundation (Latin-complete, replaces current OSK)
- A1 [DONE] Layout generator + `NanoOskLayouts.h` (21 keyboards + 49 popups).
- A2 `NanoOsk.h/.cpp`: aspect-aware box (1:1/3:2/4:3/16:9/portrait), render
  (panel, keys, focus selector w/ overshoot+click anim, query/preview line,
  action button, footer), geometric nearest-in-direction nav, shift/sym/caps,
  accent popups + long-press timer, real caret, UTF-8 buffer ops.
- A3 Integration: route the keep-stable methods + `mOsk*` members into NanoOsk;
  edit the `mOskCursorX/Y` poke sites in `NanoMenuInput.cpp`/`NanoMenuXmb.cpp`
  to call `oskMoveCursor`/`oskActivateKey`; add `NanoOsk.cpp` to `Android.bp`;
  remove the old `kOskLayout`. Verify search + Wi-Fi password + settings edit.
- A4 Language: `pickLayout` (full 16-rule chain) + in-keyboard switch key + UI
  default. Latin parity verified per language (currency keys, accents).
  MILESTONE: faithful Leanback-plus keyboard on every aspect ratio + portrait.

Phase B - Composition infra + Korean
- B1 `InputMethod` interface, composing buffer, candidate bar (render + nav).
- B2 `HangulInput` jamo automaton (no dictionary). Proves the IME plumbing.

Phase C - Cyrillic/Greek/Thai grids + RTL (Hebrew, Arabic)
- C1 New key tables for Cyrillic (ru), Greek (el), Thai (th); `*Input` plugins.
- C2 RTL field via ICU `ubidi`; `HebrewInput`; `ArabicInput` with
  `u_shapeArabic` presentation-form shaping. Field renderer becomes dir-aware.

Phase D - Chinese Pinyin
- D1 Vendor libgooglepinyin (engine + `dict_pinyin.dat`); `PinyinInput`
  producing Hanzi candidates; wire candidate bar. Build + sepolicy (read-only
  dict asset under /system).

Phase E - Japanese
- E1 romaji->hiragana/katakana composition (algorithmic) + kana commit.
- E2 kana->kanji conversion via a vendored dictionary engine (evaluate compact
  options). May ship E1 first, E2 as a follow-up.

Phase F - Device verification + polish across all scripts and aspect ratios.

## Known risks / decisions still open

- Japanese Kanji conversion is the single hardest, heaviest item (dictionary
  engine + data). Kana-only (E1) is a clean intermediate deliverable.
- libgooglepinyin licensing + dict size (~1.3MB) needs a vendoring location and
  a build wire-up; confirm acceptable to ship in /system.
- Arabic ligatures beyond lam-alef may need HarfBuzz if `u_shapeArabic` PF
  output is insufficient; PF approach covers the vast majority.
- The in-keyboard language switch set should be curated (not all ~80 locales) to
  stay usable on a D-pad.
